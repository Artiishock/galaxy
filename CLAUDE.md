# CLAUDE.md — правила разработки проекта `rezyme/web`

> Этот файл — постоянный свод правил. Claude обязан сверяться с ним **перед каждым**
> изменением кода и проверять готовый результат по чеклисту в разделе 14.
> Правила важнее привычек и важнее «быстрого решения». Отступление от правила
> допустимо только с явным обоснованием в ответе пользователю.

**Цель проекта:** сайт-эталон. Не «работает», а «так, как надо делать»: современный
стек, чистая архитектура, продуманная объектная модель 3D-слоя, безупречное SEO,
доступность и производительность.

---

## 0. Два принципиальных уточнения задачи

Их нужно помнить, потому что они определяют всю архитектуру.

**0.1. WebGL невидим для поисковиков.** Всё, что нарисовано в `<canvas>`, для краулера
не существует: ни текста, ни ссылок, ни структуры. Поэтому 3D — это **декоративный
слой поверх полноценного семантического HTML**, а не замена ему. Любая страница
обязана быть осмысленной и полностью читаемой при отключённом WebGL и JS.
Three.js — прогрессивное улучшение, никогда — носитель контента.

**0.2. «ООП» в React — не классовые компоненты.** Классовые компоненты React —
устаревший антипаттерн, их не пишем. ООП живёт в **доменном и 3D-слое**: движок сцены,
менеджеры ресурсов, объекты сцены, сервисы, репозитории. UI-слой — функциональный:
компоненты, хуки, чистые функции. Граница между этими мирами — тонкий адаптер
(раздел 5.4).

## 2. Архитектура: слои и направление зависимостей

```
src/
  app/                 # Next.js App Router: маршруты, layout, metadata, route handlers
  views/               # композиция страницы из виджетов (без бизнес-логики)
  widgets/             # самостоятельные блоки UI (Hero, ProjectsGrid, ContactForm)
  features/            # пользовательские сценарии (submit-contact, switch-theme)
  entities/            # доменные сущности UI (ProjectCard, SkillBadge)
  shared/
    ui/                # атомы дизайн-системы (Button, Text, Container)
    lib/               # утилиты, чистые функции
    config/            # константы, токены, env-схема
    assets/            # медиа, которое ИМПОРТИРУЕТСЯ кодом (проходит через сборщик)
  domain/              # ООП-ядро: модели, сервисы, порты. НЕ знает о React и о DOM
  three/               # ООП-ядро 3D: engine, объекты сцены, ресурсы, материалы
```

**Железное правило зависимостей:** зависимости идут только вниз по списку.
`domain/` и `three/` не импортируют ничего из React-слоёв. `shared/` не импортирует
ничего, кроме `shared/`. Нарушение направления — ошибка архитектуры, а не «мелочь»;
чинится переносом кода, а не импортом «наверх».

Правило одного экспорта: публичный API слоя — через `index.ts` этого слоя.
Глубокие импорты во внутренности чужого модуля запрещены.

## 3. ООП: как именно

Применять по делу, а не ради ритуала. Класс оправдан там, где есть **состояние +
жизненный цикл + инварианты**: движок сцены, пул ресурсов, доменная сущность с
правилами. Для преобразования данных — чистая функция, не класс со статикой.

**Обязательные принципы:**

- **SRP.** Один класс — одна причина для изменения. Класс, который и грузит ресурсы,
  и анимирует, и слушает ресайз — разбить.
- **Композиция вместо наследования.** Глубина наследования > 1 требует обоснования.
  Общее поведение — через интерфейсы и внедряемые стратегии.
- **DIP + явный DI.** Зависимости приходят через конструктор. Никаких синглтонов
  через модульный импорт, никакого `new` глубоко внутри логики — только в
  composition root (точка сборки приложения/сцены).
- **Программировать против интерфейса.** Порты (`interface`) в `domain/`,
  адаптеры (реализации) — снаружи. Так домен тестируется без сети и без WebGL.
- **Инкапсуляция реальная.** `#privateField` или `private` + `readonly` по умолчанию.
  Наружу — минимальный API, не публичные поля.
- **Иммутабельность в домене.** Value-объекты неизменяемы; изменение возвращает
  новый экземпляр. Мутация допустима в горячем 3D-цикле (раздел 5.3) — там это
  осознанная оптимизация.
- **Ошибки — типизированные.** Свои классы ошибок домена; результат операции, которая
  может провалиться, — `Result<T, E>`, а не «бросим и поймаем где-нибудь».
- **Никаких «менеджеров всего».** Имя класса без существительного предметной области
  (`Helper`, `Utils`, `Manager`, `Processor`) — сигнал, что модель не продумана.

**Обязателен явный жизненный цикл** у всего, что захватывает ресурсы:
интерфейс `Disposable { dispose(): void }` и симметричные `init/dispose`.

## 4. React: правила UI-слоя

- **Server Components по умолчанию.** `'use client'` — только там, где нужны события,
  состояние, браузерные API. Директива ставится максимально глубоко в дереве, чтобы
  клиентский бандл оставался маленьким.
- Классовые компоненты не пишем (исключение: `ErrorBoundary`, пока нет хука-аналога).
- Компонент — «дурак»: получает данные, рисует. Логика — в хуках и сервисах.
- Пропсы типизированы явно; никаких `React.FC`, никакого `any`, никакого
  `props: Record<string, unknown>`.
- Ключи списков — стабильные доменные id, никогда не индекс массива.
- `useEffect` — крайняя мера для синхронизации с внешним миром. Производные значения
  считаются при рендере, а не через эффект + стейт.
- Никаких «магических» строк и чисел в JSX — только именованные константы/токены.
- Загрузка данных — в серверных компонентах / route handlers; `fetch` с явными
  политиками кеширования и ревалидации.
- Границы: `error.tsx`, `loading.tsx`, `not-found.tsx` на каждом значимом сегменте.
- **Перекрывающий экран слой обязан быть невидим в серверной разметке.** Заставка,
  модальное окно, прелоадер: если их видимость выведена из состояния, которое на
  сервере означает «показываем», то без JavaScript слой останется навсегда —
  скрыть его будет некому. Видимость привязывается к данным, появляющимся только
  после гидратации, и проверяется по собранному HTML, а не по виду в браузере.
- **Заставка не должна быть обязательной.** Пропуск по `prefers-reduced-motion`,
  обрыв по любому действию пользователя (клик, клавиша, прокрутка) и отсутствие
  при заходе по прямой ссылке на внутреннюю страницу.

## 5. Three.js: правила 3D-слоя

### 5.1. Изоляция и загрузка

- Ядро three.js подключается динамическим `import()` **внутри эффекта**, а не
  статическим импортом: так оно не попадает в основной бандл и грузится после
  гидратации. `dynamic(..., { ssr: false })` на компонент-обёртку не годится —
  вместе с 3D из HTML исчезла бы и разметка навигации (§0.1).
- Компонент со сценой при этом остаётся SSR-совместимым: холст декоративен,
  а весь смысловой DOM рендерится на сервере.
- Canvas не блокирует LCP: критический контент страницы рендерится и виден до того,
  как загрузится сцена. Сцена инициализируется по `IntersectionObserver` /
  после interactive.
- Тяжёлые ассеты (модели, HDRI, текстуры) — вне основного бандла, форматы
  **glTF + Draco/Meshopt**, текстуры **KTX2/Basis**, а не PNG на 8 МБ.

### 5.2. Объектная модель сцены

Ядро в `src/three/` — чистый TypeScript, без React:

- `Engine` — владеет renderer, scene, camera, часами и render-loop. Ничего не знает
  о конкретных объектах.
- `SceneObject` (абстракция) — базовый контракт: `object3d`, `update(dt, ctx)`,
  `dispose()`. Конкретные объекты реализуют его.
- `ResourceRegistry` — единая точка учёта geometry/material/texture; на `dispose`
  освобождает **всё** захваченное.
- Системы (`RaycastSystem`, `ResizeSystem`, `PostFxSystem`) — независимые модули,
  подключаемые в composition root сцены.

### 5.3. Производительность рендера (жёстко)

- **Ноль аллокаций в кадре.** Никаких `new THREE.Vector3()` / литералов объектов /
  замыканий внутри `useFrame`/`update`. Временные векторы — переиспользуемые поля
  класса или модульные константы.
- Никакого `setState` на каждый кадр. Анимация мутирует объекты напрямую.
- Инстансинг (`InstancedMesh`) для повторяющейся геометрии; шаринг материалов;
  минимум draw calls.
- Всё, что не двигается: `matrixAutoUpdate = false`, статические геометрии — общие.
- Кадр не зависит от FPS: используем `delta`, а не «шаг за кадр».
- **Непрерывное вращение накапливаем углом, а не прибавкой к `rotation`.**
  Прибавление дельты к Эйлеровым углам каждый кадр за долгую сессию накапливает
  ошибку и уводит наклон объекта. Правильно: базовая ориентация — кватернион,
  угол поворота — число, итоговый кватернион собирается заново каждый кадр.
  Заодно это делает состояние воспроизводимым.
- `dispose()` обязателен для geometry, material, texture, render targets, а также
  снятие всех слушателей. Утечка GPU-памяти при уходе со страницы — баг уровня блокера.
- Пиксель-рэйшо ограничен: `Math.min(devicePixelRatio, 2)`.
- Деградация: при слабом устройстве / низком FPS — упрощённая сцена или статический
  постер. Определять по фактическому FPS, а не по user-agent.
- **Преломление (`transmission`) видит только содержимое сцены.** three рисует
  отдельный проход в буфер и берёт картинку оттуда; `scene.background` в этот
  буфер попадает, а HTML-слой за холстом — нет. Поэтому прозрачный объект над
  HTML-фоном преломляет пустоту и выглядит тёмной дырой: фон обязан быть внутри
  WebGL. Стоимость прохода снижается `renderer.transmissionResolutionScale`:
  преломление размыто шероховатостью, и половинное разрешение незаметно.
- **Чтобы текстура показывала свой цвет, нейтральным должно быть всё, что на неё
  влияет.** Источников окраски всегда несколько: множитель `color` материала,
  собственное свечение (`emissive`), аддитивные спрайты поверх и — сильнее
  прочего — цвет источников света. Насыщенный свет перекрашивает вообще всё, что
  освещает. Проверять цепочку целиком, а не один параметр.
- **Цветовое пространство текстур разделяется по смыслу.** Базовый цвет — sRGB,
  карты данных (нормали, шероховатость, металличность) — линейные. Ошибка тихая:
  ни исключения, ни предупреждения, просто блёклая или пережжённая поверхность.
- **Однородная карта — это число, а не файл.** Перед подключением текстуры
  проверять, есть ли в ней вариация: плоская карта нормалей или ровный ORM дают
  тот же результат, что константа в материале, но стоят запроса и памяти.
- **Текстурам нужна честная UV-развёртка.** `IcosahedronGeometry` склеивает UV
  заплатками по шву — текстура плывёт у полюсов. Для текстурированных сфер
  `SphereGeometry`.
- **Постобработка — последнее средство.** Depth of field, свечение и подобные
  эффекты сначала пробуем получить построением сцены: крупный мягкий спрайт у
  камеры выглядит расфокусированным сам по себе, а аддитивный ореол заменяет bloom.
  EffectComposer добавляет полноэкранные проходы и вес бандла ради того, что часто
  достигается размещением объектов.
- Декоративное наполнение расставляется **детерминированным** генератором с
  фиксированным seed: композиция стабильна между заходами, её можно осознанно
  подбирать, а случайный разброс не выдаётся за «живость».

### 5.4. Мост React ↔ ООП

Единственная точка связи — тонкий хук (`useCosmos`), который создаёт ядро один раз
в `useEffect`, отдаёт императивный API наружу через ref и **гарантированно вызывает
`dispose()` в cleanup** (в т.ч. корректно при двойном монтировании в StrictMode).

**Интерактивные объекты сцены живут в DOM, а не в canvas.** Кликабельный объект —
это настоящий `<a>`/`<button>` в серверной разметке; 3D-слой лишь передаёт ему
экранные координаты (проекция мировой позиции) и двигает его `transform`. Так
кнопка остаётся кнопкой для поисковика, клавиатуры и скринридера. Ловля кликов
рейкастом по canvas — запрещена как единственный способ навигации.
Позиции пишутся в `style.transform` и CSS-переменные, только при фактическом
изменении; ни `setState`, ни чтения геометрии DOM в кадре.

**У камеры ровно один владелец.** Все режимы (параллакс, подлёт к объекту,
возврат) считаются в одном классе и смешиваются коэффициентом, после чего камере
присваивается один результат за кадр. Два независимых источника, пишущих
`camera.position`, затирают друг друга — и это не воспроизводится стабильно.
Смешивание поз вместо переключения заодно даёт плавный перелёт бесплатно.

**Состояние сцены выводится из маршрута, а не из обработчика клика.** Какой
объект в фокусе — следствие текущего URL. Тогда камера ведёт себя одинаково при
клике, при кнопке «назад» и при открытии страницы по прямой ссылке, а состояние
сцены не может разойтись с тем, что показано на экране.

**Сцена живёт в layout, а не на странице.** Корневой layout при навигации не
размонтируется, поэтому движок не перезапускается: состояние сцены непрерывно, и
возврат на главную не «отматывает» орбиты в начало. Контент маршрута рендерится
слоем поверх сцены. Класть сцену внутрь `page.tsx` запрещено — это гарантирует
пересоздание движка на каждом переходе.

**Траектория рисуется целиком, одной линией и одним цветом.** Орбита
детерминирована — это маршрут, а не след. Подвижный сегмент другого цвета,
ползущий за объектом, читается как дефект: линия выглядит собранной из разных
кусков. Вид траектории меняется только в ответ на действие пользователя
(наведение, фокус) — и меняется яркость, а не цвет.

Общее правило: **самостоятельное движение допустимо только там, где оно
моделирует что-то реальное** — вращение тел, дрейф звёзд. Декоративная анимация
поверх статической по смыслу сущности лишь дробит её восприятие.

### 5.5. Уважение к пользователю

- `prefers-reduced-motion: reduce` → анимации выключаются или сводятся к статике.
  Это правило, а не опция.
- Рендер-луп останавливается, когда вкладка скрыта или canvas вне вьюпорта.
- Сцена не перехватывает скролл и фокус клавиатуры без явной необходимости.

## 6. SEO: обязательная программа

- **Контент рендерится на сервере.** Проверка: `curl` страницы возвращает весь
  значимый текст и ссылки. Если контент появляется только после гидратации — это баг.
- **Семантическая разметка.** Один `<h1>` на страницу, корректная иерархия заголовков,
  `<main>/<nav>/<article>/<section>`, списки — списками. `<div>` вместо кнопки/ссылки
  запрещён.
- **Metadata API** Next.js: `title` (шаблон + уникальный на страницу), `description`,
  `canonical`, Open Graph, Twitter Card, `robots`. Динамические страницы —
  `generateMetadata`.
- **OG-изображения** генерируются через `opengraph-image` (ImageResponse), а не
  прибиты одной картинкой на весь сайт.
- **JSON-LD** (`schema.org`) для типа контента: `Person`/`Organization`, `WebSite`,
  `BreadcrumbList`, для резюме/портфолио — `Person` + `hasOccupation`, для статей —
  `Article`. Валидировать в Rich Results Test.
- **`sitemap.ts` и `robots.ts`** — генерируемые, не статические файлы «руками».
- **Ссылки** — `next/link`, осмысленный анкор («Смотреть проект X», не «здесь»),
  внешние — с `rel` по смыслу.
- **Изображения** — `next/image`, обязательный содержательный `alt` (у декоративных
  — пустой `alt=""`), явные размеры (борьба с CLS), `priority` только для
  LCP-изображения.
- **Где лежит медиа — решает способ его использования, а не тип файла:**
  - `src/shared/assets/` — то, что импортируется кодом. Статический импорт даёт
    сборщику размеры, хеш в имени и `blurDataURL`. Так работают изображения
    под `next/image`.
  - `public/` — то, что отдаётся как есть по фиксированному URL. У Next нет
    конвейера оптимизации видео (подтверждено доками установленной версии),
    поэтому видео всегда сюда; сюда же `robots.txt`, favicon, og-фолбэк.
  - `assets/` в корне — мастер-исходники, из которых собраны файлы в `public/`.
    В сборку не попадают, но нужны для повторной перекодировки.
- Разрешение исходника проверять под самый большой целевой экран: `next/image`
  уменьшает изображение, но не увеличивает — растянутый фон выглядит мылом.
- **Фоновое видео:** без атрибута `autoplay` (запуск из хука после проверки
  `prefers-reduced-motion`), обязательно `muted`, `loop`, `playsInline`,
  `preload="none"` и `poster`; `aria-hidden` и `tabIndex={-1}`, потому что
  декорация не участвует в навигации.
- **Формат медиа выбирается замером, а не репутацией кодека.** Перед заменой
  формата перекодировать в кандидатов и сравнить размеры при сопоставимом
  качестве. Проверено на фоновом ролике: при равном качестве AV1 (246 КБ) и
  VP9 (241 КБ) проиграли H.264 (211 КБ) — вес держали разрешение и частота
  кадров, а не кодек. Сначала уменьшаем разрешение и fps под фактическую задачу,
  и только потом смотрим на кодек.
- **Шрифты** — `next/font` (self-hosted, `display: swap`, подмножества). Внешних
  запросов к шрифтовым CDN нет.
- **URL** — человекочитаемые, стабильные, в нижнем регистре, без параметров-мусора.
  Изменение URL → 301.
- **i18n** (если появятся языки): `hreflang`, локализованные метаданные, `lang` на `<html>`.
- **Core Web Vitals — бюджет:** LCP < 2.0 s, INP < 200 ms, CLS < 0.1 на 4G/среднем
  мобильном. 3D не имеет права нарушить этот бюджет — если нарушает, режем 3D.
- Lighthouse на прод-сборке: **Performance ≥ 90, Accessibility / Best Practices /
  SEO = 100**. Ниже — работа не закончена.

## 7. Доступность (WCAG 2.2 AA) — не «потом»

- Полная работа с клавиатуры, видимый `:focus-visible`, логичный порядок табуляции.
- Контраст текста ≥ 4.5:1 (крупный — ≥ 3:1).
- Формы: `<label>` для каждого поля, ошибки связаны через `aria-describedby`,
  сообщения — в `aria-live`.
- ARIA только когда нативной семантики не хватает. Правильный `<button>` лучше
  любого `role="button"`.
- `<canvas>` с декоративной сценой — `aria-hidden="true"`, вне порядка табуляции.
- Проверка: `axe` в Playwright-тестах, прогон с клавиатуры и со скринридером.

## 8. Стили и дизайн-система

- Дизайн-токены (цвет, типографика, отступы, радиусы, тени, длительности) — CSS-переменные
  в одном месте; в компонентах используются только токены, не сырые значения.
- Тёмная/светлая тема — через переопределение токенов, поддержка
  `prefers-color-scheme` + осознанный выбор пользователя.
- Mobile-first, `clamp()` для типографики, `container queries` где уместно.
- Никаких `!important` и магических z-index — шкала слоёв задаётся токенами.
- **Опечатка в имени токена молча стирает свойство целиком.** `var(--нет-такого)`
  делает значение невалидным на этапе вычисления, и браузер отбрасывает всё
  объявление — `padding: clamp(var(--space-5), …)` при отсутствующем `--space-5`
  даёт нулевой отступ, а не запасной. Ошибка не видна ни линтеру, ни сборке.
  Перед сдачей сверять используемые `var(--…)` со списком объявленных.
- **Раскладку блока внутри узкой панели определяет `@container`, а не `@media`.**
  Медиазапрос смотрит на окно: на широком мониторе он сработает и для колонки,
  которая сама по себе узкая, и разложит её так, будто места много.
- **Прокручиваемый контейнер в grid обязан иметь ограниченную строку.** Неявная
  строка `auto` растягивается под содержимое, `max-height: 100%` считается от неё
  же и никогда не срабатывает: блок вырастает выше экрана, внутренней прокрутки
  не возникает, колесо мыши «не работает». Нужны `grid-template-rows: minmax(0, 1fr)`
  у родителя и `min-block-size: 0` у прокручиваемого потомка.
- **Кастомная полоса прокрутки не заменяет прокрутку.** Контейнер остаётся
  `overflow: auto`, нативная полоса просто скрывается (`scrollbar-width: none`
  плюс `::-webkit-scrollbar { display: none }`), а своя рисуется поверх. Перехват
  `wheel` и ручной пересчёт `scrollTop` ломают тачпад, инерцию, клавиатуру и
  `scrollIntoView`. Сам контейнер получает `tabIndex` и имя — прокрутка должна
  работать с клавиатуры (WCAG 2.1.1).
- Анимации: `transform`/`opacity` (композитные свойства), длительности из токенов.

## 12. Протокол актуальности и защищённости решений

Знания модели имеют дату отсечки и **устаревают**. Экосистема (Next, React, three,
TypeScript) движется быстрее. Поэтому любое техническое решение проходит проверку
фактами, а не памятью.

### 12.1. Правило «проверяй, а не вспоминай»

Проверка **обязательна** перед тем, как:

- назвать или зафиксировать версию пакета;
- использовать API фреймворка, про который «известно, что он такой»;
- утверждать, что что-то deprecated / поддерживается / несовместимо;
- добавить или обновить зависимость.

Инструменты проверки (в порядке предпочтения):

1. **`node_modules/next/dist/docs/`** — документация ровно той версии Next, которая
   установлена. Самый точный источник из существующих. Сам Next 16 предупреждает,
   что его API расходится с тем, что «помнит» модель, и дописывает эту напоминалку
   в конец CLAUDE.md — блок `nextjs-agent-rules` создан инструментом,
   удалять его бесполезно и не нужно.
   Цена незнания на живом примере: в Next 16 `middleware.ts` переименован в `proxy.ts`.
2. `npm view <pkg> version` / `peerDependencies` / `dist-tags` — факт из реестра;
3. **содержимое установленного пакета** (`package.json` → `exports`, наличие API,
   `node -e "require(...)"`) — когда проверять надо не номер версии, а фактические
   возможности. Именно так вскрылось, что в TypeScript 7 нет JS-API компилятора;
4. официальная документация и CHANGELOG релиза;
5. `npm audit`, GitHub Security Advisories — для уязвимостей;
6. фактическая сборка/тест — окончательный аргумент.

**Запрещено** писать версии, флаги конфигов и сигнатуры API по памяти и подавать это
как проверенный факт. Если проверить возможности нет — сказать прямо: «не проверено,
подтверждается так-то».

Отдельно: **мажорные обновления меняют CLI и конфиги.** Например, TypeScript 7 —
нативный порт компилятора; прежде чем прописывать `tsc --noEmit` в CI, проверить
фактическое имя и флаги бинарника в установленной версии. То же для ESLint 10
(flat config), Vitest 5, Next 16 — не переносить конфиг «как помнится из прошлой мажорки».

### 12.2. Что значит «новейшее»

Приоритет: **новейшее из того, что стабильно и совместимо**. Порядок отсева:

1. отбрасываем alpha/beta/rc/canary — в основную ветку не идут;
2. отбрасываем версии, ломающие peer-совместимость соседей по стеку;
3. отбрасываем версии моложе ~1–2 недель без явной нужды (ранние регрессии);
4. из оставшегося берём максимальную.

Гнаться за latest ценой конфликта или нестабильности — **ошибка**, а не смелость.
Каждое сознательное отставание от latest фиксируется в матрице 1.1 с причиной и
условием снятия ограничения.

### 12.3. Уязвимости и «наименьшая уязвимость»

- `npm audit` — часть CI; уровни `high`/`critical` блокируют мерж.
- Транзитивные уязвимости чиним `pnpm.overrides`, а не игнорируем.
- Меньше зависимостей = меньше поверхность атаки. Пакет с одним автором, без релизов
  год, с десятками транзитивных зависимостей — не берём.
- Lock-файл коммитится всегда; CI ставит зависимости `--frozen-lockfile`.
- Обновления зависимостей — регулярные и малыми порциями (Dependabot/Renovate),
  а не «раз в год большим прыжком».
- Безопасность рантайма — раздел 10; здесь речь про безопасность **цепочки поставок**.

### 12.4. Ревизия решений

- Матрица версий (1.1) перепроверяется при каждом заходе в проект после паузы и
  перед любым обновлением зависимостей; дата проверки обновляется в файле.
- Если проверка показала, что ранее принятое решение устарело или стало уязвимым —
  сказать об этом **сразу**, не дожидаясь вопроса, и предложить миграцию.
- Правило самопроверки: прежде чем ответить «сделано верно», задать себе вопрос
  «на чём основано — на факте из реестра/доков или на воспоминании?». Второе —
  повод пойти и проверить.
